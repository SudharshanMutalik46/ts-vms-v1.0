# Phase 4.2: Recording Service Foundation

## Process Model
The `vms-recording` service is a standalone daemon. 
* **Supervisor:** Runs a background evaluation loop (e.g., every 1 second) reconciling desired states against actual states.
* **Camera Worker:** An isolated thread (goroutine) dedicated to a single camera. In Phase 4.3, this thread will hold the GStreamer pipeline and File IO handles. If a worker crashes, it does not bring down the supervisor.

## Scheduling Model
1. **24x7:** Always returns `true`.
2. **Time Window:** Checks current `Weekday` and `HH:MM` against configured rules.
3. **Event Triggered:** Maintains an active deadline. When an API call (`/api/v1/recording/trigger`) fires, it extends the recording deadline by `N` seconds (post-buffer).

## License & RBAC Gates
* **License:** `LicenseGate.TryAcquire()` is called by the Supervisor before starting a worker. If `Active >= Quota`, the camera remains stopped but gets tagged `THROTTLED_BY_LICENSE` so operators know they are dropping frames due to licensing.
* **RBAC:** All HTTP control endpoints check the `Authorization` header. They enforce the `recording.manage` scope. (A dev-bypass flag is provided for initial integration).

## Health Signals & Crash Recovery
* **Endpoints:** `/healthz` (liveness), `/readyz` (depends on Recovery completion), `/status` (JSON dump of all workers).
* **Recovery:** On boot, the service looks for `vms-recording.pid`. If found, it indicates an unclean shutdown. It triggers `IRecoveryHooks` to allow Phase 4.3 to repair fragmented MP4 containers before new workers are spawned.

## Windows Service
Packaged using **WinSW** (Windows Service Wrapper). This avoids linking complex native C-hooks into the Go code, enables automatic log rotation on standard out, and ensures crash restarts at the OS level.
