# Phase 4.11 - CPU Profiling & Hotspot Fixes

## Profiling Method
* **Tool:** Windows Performance Analyzer (WPA) via Event Tracing for Windows (ETW).
* **Workload:** 128 active recording pipelines.

## Identified Hotspots & Applied Fixes

1. **Hotspot:** `g_log_default_handler` (GStreamer internal logging).
   * **Impact:** Accounted for ~34% of total CPU cycles due to string formatting and thread synchronization on `stdout` for hidden INFO logs.
   * **Fix:** Forced `GST_DEBUG=1` (WARNING and above only) in the VMS environment bootstrap.
   
2. **Hotspot:** `sync.RWMutex.RLock` in Phase 4.9 `health.Manager`.
   * **Impact:** The background evaluator was locking the global map lock 128 times per second, causing massive L3 cache invalidation and thread contention.
   * **Fix:** Switched to a partitioned/sharded map design and relied entirely on `atomic.AddUint64` for the telemetry hot-path (bytes written, frames dropped). Global lock is only used on camera add/remove.

3. **Hotspot:** MP4 Muxer `moov` atom reallocation.
   * **Impact:** Standard `mp4mux` caches the entire index in memory and continuously reallocates the buffer as the file grows, causing GC pressure and CPU spikes at the end of a 5-minute segment.
   * **Fix:** Enabled `fragment-duration=1000`. The muxer now writes a tiny `moof` + `mdat` every second, completely flattening the CPU curve and memory allocation rate.

**Result:** CPU usage stabilized at **~14%** for 128 cameras (well below the 80% limit).
