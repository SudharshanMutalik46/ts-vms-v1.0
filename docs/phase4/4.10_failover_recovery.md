# Phase 4.10 - Failover & Recovery (Recording)

## 1. Automatic Restart Strategy
The `vms-recording` service is registered as a Windows Service. To ensure high availability, we leverage the Windows Service Control Manager's built-in Recovery options:
- **First failure**: Restart the Service.
- **Second failure**: Restart the Service.
- **Subsequent failures**: Restart the Service.
- **Restart Delay**: 5 seconds.
- **Reset failure count**: After 1 day.

## 2. State Recovery from Metadata Database
Upon booting, the `RecoveryManager` establishes state before enabling active streaming workers:
- **Last Finalized Segment**: Queries the `recording_segments` table for the greatest `end_ts` per camera. This serves as the "resume baseline".
- **Desired State**: Queries `recording_schedules` to determine if a camera *should* currently be recording based on the active time window.
- **Degraded Mode**: If the database is inaccessible, `db_required_for_ready` dictates behavior. If `true`, the service refuses to become `/readyz` until the DB connects. If `false`, it attempts a pure filesystem-based recovery but emits `recording.recovery.degraded` alerts.

## 3. Resume Algorithm
When resuming a camera that should be recording:
1. Fetch the DB's `last_good.end_ts`.
2. The next segment's start time will be computed strictly as `max(last_good.end_ts, time.Now())`.
3. The writer guarantees strictly increasing filenames/timestamps to prevent accidental overwrites. Quarantine any `.mp4` corrupt files that conflict.

## 4. Orphaned File Cleanup
Before worker creation, an initialization scan is fired:
* `*.tmp` files exceeding TTL are purged (from Phase 4.3).
* **Disk vs DB Reconciliation**: If an `.mp4` file is on disk but missing from the DB, we log a backfill warning. If an expected `.mp4` is in the DB but missing from the disk, it is marked as `missing` but NOT explicitly removed from the index without user input.

## 5. Health Model
- **Liveness (`/healthz`)**: Returns 200 OK instantly if the HTTP server is up.
- **Readiness (`/readyz`)**: Returns 200 OK only if the DB is connected (unless degraded mode is allowed), Scheduler initialized, and the Circuit Breaker is *not* locally engaged.
- **Status (`/status`)**: Exposes camera states, resume `baseline_ts`, `restart_count`, and boolean `circuit_breaker_active`.

## 6. Disk Circuit Breaker
A globally initialized background loop tracks disk free space dynamically.
* **Trigger**: If active volume free space < `crit_free_gb`, or disk usage > `crit_usage_percent`.
* **Engagement Action**:
    1. Immediately prevents new segment allocation.
    2. Sends graceful `Stop()` to `SegmentWriter` to flush in-flight data safely.
    3. Sets state to `FAILED` with `circuit_breaker_active = true`.
* **Recovery Action**:
    1. Once space rises above `warn_free_gb`, the breaker releases.
    2. Modifies state back to `RECOVERING` / `ACTIVE` and pipeline spins up.
